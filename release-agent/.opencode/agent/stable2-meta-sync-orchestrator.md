# Agent: stable2-meta-sync-orchestrator

## Purpose
Run the post-PR-collection stable2 sync flow in this order:
1. Run GitHub repo cherry-pick script for READY PR commits across PR-derived repos
2. Report partial successes/conflicts and allow manual conflict resolution outside automation
3. Create the bi-weekly stable2 sync Jira tracking ticket and link every ticket successfully
   cherry-picked this cycle to it with a `deploys` link — its key becomes the Gerrit topic
   used in Phase 6, since that's needed before any Gerrit push happens
4. Add `track_for_stable2_considered` only after cherry-pick phase is complete
5. Create GitHub stable2 release tags on the user-confirmed GitHub branch (default
   `support/stable2`, see "Before Starting" step 4) for successfully cherry-picked repos
6. Update `generic-pkgrev.inc` and `generic-srcrev.inc` locally for successfully tagged repos
7. Invoke `gerrit-cherrypick-squash` (existing dependency traversal behavior unchanged), using
   the tracking ticket's key as the Gerrit topic, and include meta-rdk-broadband updates under
   that same topic

## Critical Constraints — Read First
- Eligibility is determined from READY Jira tickets in `stable2_status_analysis.yaml`
- GitHub repo mapping comes from `pr_list.yaml`
- Do NOT include repos that are not associated with READY tickets
- This agent does NOT replace the existing stable2 release orchestrator; it runs after Phase 5/manual review
- Direct script cherry-pick is for GitHub repositories only and is independent from Gerrit topic operations
- `gerrit-cherrypick-squash` is Gerrit-only and must remain separate from GitHub script cherry-pick intent
- Cherry-pick phase must process all targeted repos and may finish with partial success
- If some repos fail/conflict, continue flow for successful repos only and print manual actions for failed repos
- The tracking ticket must be created right after cherry-pick (Phase 3), before tagging/SRCREV/Gerrit —
  its key is the Gerrit topic used in Phase 6, and Gerrit topics/commit references can't reference a
  ticket that doesn't exist yet
- Considered labeling must happen after cherry-pick phase completion
- Tagging and SRCREV prep must use successful repo scope only
- Gerrit topic must be shared across the meta-rdk-broadband change and the normal Gerrit cherry-pick changes
- `gerrit-cherrypick-squash` behavior must remain unchanged except for optional inclusion of prepared meta-layer file updates
- Every phase must print its planned repo/tag/SHA/file actions and wait for explicit confirmation before mutating anything
- If `--dry-run` is present, print the same reports and planned actions but do NOT create releases, edit files, commit, or push
- Phase 1 must append every ticket it cherry-picks successfully to `cherry_picks_done` in
  `release_session.yaml` (create the file/list if absent) — this is the only source of truth
  Phase 3's tracking ticket uses; do not skip this even in `--dry-run` (still append there, just
  don't create Jira/GitHub/Gerrit changes)
- **Output format consistency — ALL 6 phases, every run:** every printed
  report/plan/table in this agent (Phase 1's cherry-pick summary, Phase 4's
  tagging plan, Phase 5's SRCREV resolution report, Phase 6's Gerrit
  confirmation, etc.) must use the exact same fixed, deterministic layout
  every single run — same headings, same fields, same structure. Never vary
  a report's shape based on `--dry-run`, `--test-repo`, or how many
  repos/tickets/PRs are involved this run — only the actual data inside that
  fixed layout changes. Same standing rule as `stable2-release-orchestrator.md`'s
  own copy of this constraint; it applies here too since this agent is
  invoked as that orchestrator's Phase 5.

## Workflow Overview

```text
GitHub branch + Gerrit branch resolved and confirmed with the user ("Before Starting" step 4)
  -> READY tickets from stable2_status_analysis.yaml
  -> mapped to repos via pr_list.yaml
  -> GitHub repo cherry-pick script for READY PR commits onto {github_branch}
  -> partial success summary (success repos + conflict repos)
  -> successful cherry-picks appended to cherry_picks_done in release_session.yaml
  -> create bi-weekly stable2 sync Jira Task + deploys links to every cherry-picked ticket
     (its key = the Gerrit topic used later)
  -> add track_for_stable2_considered after cherry-pick completion
  -> GitHub stable2 releases on {github_branch} for successful repos
  -> local generic-pkgrev.inc update on meta-rdk-broadband {gerrit_branch} branch (successful repos)
  -> SHA resolution and local generic-srcrev.inc update on meta-rdk-broadband {gerrit_branch} branch (successful repos)
  -> gerrit-cherrypick-squash on {gerrit_branch}, topic = tracking ticket key
```

## PHASE 1: GitHub Repo Cherry-Pick (Step-by-Step)

**Script:** `scripts/cherry_pick_to_stable2.py`

This phase runs first and attempts cherry-picks across PR-derived repos.
Partial success is allowed.

Prompt:
```text
Proceed with Phase 1 (GitHub repo cherry-pick)? [Y/n]
```

Run with these rules:
1. Read `stable2_status_analysis.yaml` and keep only `readiness == "READY"`
2. Read `pr_list.yaml`
3. Build repo scope from READY PR entries in `pr_list.yaml` (default behavior)
4. Optionally narrow to one repo only when user provides `--repo`
5. Cherry-pick matching READY commits to `{github_branch}` (core-nw repos) or
   `{mesh_github_branch}` (GDCS repos) — resolved in "Before Starting" step 4,
   never the hardcoded `support/stable2` default
6. If conflict/error in a repo, report repo + commit ids and continue other repos

**Run as two separate invocations when GDCS repos are present in scope** —
`cherry_pick_to_stable2.py` only works under ONE active `gh`/git credential
identity at a time, and `rdk-gdcs` repos need `$GH_MESH_USER` while
`rdkcentral` repos need the default identity (same rule as
`on-demand-cherry-pick.md`'s "GitHub Identity — Per-Repo Org Switch"):

1. Record `{default_gh_user}` (`gh auth status --hostname github.com`,
   the account with `Active account: true`).
2. Run the core-nw batch first, under `{default_gh_user}` (already active,
   no switch needed), scoped with `--github-org rdkcentral`:
   ```bash
   python3 scripts/cherry_pick_to_stable2.py --branch {github_branch} --github-org rdkcentral {dry_run_flag}
   ```
3. If GDCS repos are in scope, switch identity: `gh auth switch --hostname
   github.com --user "$GH_MESH_USER"` (STOP if `$GH_MESH_USER` is unset —
   do not guess), verify with `gh auth status`, then run:
   ```bash
   python3 scripts/cherry_pick_to_stable2.py --branch {mesh_github_branch} --github-org rdk-gdcs {dry_run_flag}
   ```
   If a GDCS lookup 404s even with `$GH_MESH_USER` active, that means the
   token needs SSO authorization for `comcast-global` — tell the user,
   don't conclude the repo is missing.
4. Switch back to `{default_gh_user}` immediately after the GDCS batch
   completes (success or failure) — before moving to Phase 1's
   `release_session.yaml` update below.

Suggested commands for narrower/manual runs (always pass `--branch` explicitly
— do not rely on the script's own `support/stable2` default; pass
`--github-org` too when you know which identity is already active):

Single repo apply and push:
```bash
python3 scripts/cherry_pick_to_stable2.py --repo <org/repo_or_url> --branch {github_branch}
```

Single repo apply without push:
```bash
python3 scripts/cherry_pick_to_stable2.py --repo <org/repo_or_url> --branch {github_branch} --no-push
```

Manual cherry-pick for specific commits:
```bash
python3 scripts/cherry_pick_to_stable2.py --repo <org/repo_or_url> --branch {github_branch} --commits <commit_id_1,commit_id_2>
```

After both batches finish, before printing the Phase 1 report, update `release_session.yaml`:
- For every ticket the script's own "SUCCEEDED" report lists, look up that ticket's full entry
  in `pr_list.yaml` (`ticket`, `repo`/component, `number`, `merge_commit_sha`) — use the full
  40-char SHA from `pr_list.yaml`, not the truncated one the script prints.
- Append one entry per successfully cherry-picked ticket to `cherry_picks_done` in
  `release_session.yaml` (create the key as an empty list first if the file has none):
  ```yaml
  cherry_picks_done:
    - ticket: "RDKB-66213"
      pr_number: 94
      component: "utopia"
      merge_commit_sha: "3a9108f039..."
  ```
- Do this even in `--dry-run` (Phase 2 needs it to produce a meaningful preview) — it's a local
  bookkeeping file, not a GitHub/Gerrit/Jira mutation.
- Do NOT add entries for skipped or conflicted tickets.

After completion print:
```text
PHASE 1 COMPLETE
Results:
  Successful repos: {S}
  Repos with conflicts/errors: {F}
  Tickets appended to cherry_picks_done: {T}

Action required for failed repos:
  - Show failing repo, commit ids, and manual cherry-pick instruction

Proceed to Phase 2? [Y/n]
```

## PHASE 2: Create Bi-weekly Stable2 Sync Jira Ticket

**Skill:** `stable2-release-tracking-ticket`

Runs immediately after cherry-pick, before anything touches Gerrit — its key becomes the
Gerrit topic in Phase 6, and Gerrit topics/commit references can't point at a ticket that
doesn't exist yet.

This phase will:
- read `cherry_picks_done` from `release_session.yaml` (populated by Phase 1 of this
  orchestrator — not by any other skill)
- compute the date range: `cycle_start` from `release_session.yaml` (set by `/main-tagging`)
  through today
- print a clean table of tickets to link (Jira, PR #, component, commit SHA)
- print the proposed new Jira ticket fields
- ask for confirmation before creating the ticket or adding any links
- create an RDKB Task titled `[{start_date}] - [{end_date}] bi-weekly stable2 sync`
- add outgoing `deploys` links to each successfully cherry-picked ticket
- update `release_tracking_jira` in `release_session.yaml`

If `release_session.yaml` has no `cherry_picks_done` entries (e.g. this orchestrator was run
starting from Phase 3+ and Phase 1 never ran), warn and ask before creating a ticket with no
links, exactly as `stable2-release-tracking-ticket`'s own SKILL.md specifies.

**If the user declines at any of that skill's confirmation prompts (empty-links warning, or
the final "Create this tracking ticket...?" prompt), or `release_session.yaml` is missing
entirely:** treat this as "no tracking ticket created" for this run — do NOT abort the
orchestrator. Continue straight to the Phase 2 completion print below with
`{tracking_ticket_key}` reported as `(none created)`, then still ask to proceed to Phase 3.
Phase 6 already has a fallback for this exact case (manual Gerrit topic entry).

In `--dry-run`, no real ticket is created, so Phase 6 later falls back to asking the user for
a Gerrit topic (see Phase 6's dry-run handling below).

## PHASE 6: Gerrit Cherry-Pick + Meta Sync (Gerrit-Only)
