# GitHub Release Scripts

Release automation toolkit for Mesh Components under the `rdk-gdcs` GitHub organization. Used by the Mesh Maintainers team to coordinate and execute multi-repository releases.

## Prerequisites

See [Prerequisites](PREREQUISITES.md) for required tools, authentication, MCP server configuration, and OpenCode skills setup.

## Workflow

There are two ways to run the release process: the **fully autonomous pipeline command** (recommended), or the **individual skills** invoked manually for a read-only report and/or a standalone Jira ticket update.

### Option A: Autonomous Pipeline Command

Run the `/github-release-pipeline` command in OpenCode:

```
> /github-release-pipeline
```

This command (defined in `.opencode/commands/github-release-pipeline.md`, workflow in `.opencode/prompts/github-release-pipeline-workflow.md`) runs the entire process end-to-end with **exactly one mandatory stop** before the irreversible stage-2 release:

1. **Backs up** any existing `release-config.json` (no confirmation needed)
2. **Delegates data gathering** to the `github-release-report` skill (see Option B, Step 1) to get unreleased commits and Jira status
3. **Validates commits** against the latest tag on `main`
4. **Auto-reverts** commits tied to non-approved/non-ready Jira tickets, and skips repos where all commits were reverted
5. **Auto-classifies release type** per repo (minor if any `feature/*` branch is included, otherwise patch) — never auto-selects major
6. **Writes `release-config.json`**, including a per-repo `summary` field documenting every autonomous decision
7. **Creates/updates the Jira release ticket** automatically via the `jira-release-ticket` skill
8. **Runs pipeline stage 1** (`./release-pipeline.sh -f release-config.json -s 1`) to create release branches and open PRs
9. **Updates the Jira ticket** with the stage-1 PR links
10. **Stops and waits for user confirmation** — the agent will never run stage 2 (`-s all`) itself; you must run it yourself once PRs are reviewed/approved
11. After you run stage 2, resume the session to update the Jira ticket with the final PR merge commit hashes

See the [External Action Safety](.opencode/prompts/github-release-pipeline-workflow.md) section in the workflow file for the exact non-overridable restrictions on what the agent may and may not do.

### Option B: Individual Skills

#### 1. Read-Only Release Report

Run the `github-release-report` skill to scan mesh component repositories and produce a read-only report. This skill **never writes files, creates branches/PRs/tags, or runs scripts** — it only queries GitHub and Jira.

```
> Use the github-release-report skill to find unreleased commits
```

The skill will:

1. **Scan the component repositories** in parallel for unreleased commits (commits in `develop` not in `main`)
2. **Output a tracking table** with columns: Commit Date, Commit ID, Jira ID, GitHub PR develop, Component Release Version, GitHub PR main, Component Release Commit Hash
3. **Query Jira status** for all identified tickets — warns if any are not `RM Approved`, `Ready for Release Test`, or `Ready for Patch Test`
4. **Flag revert candidates** — a final "Commits flagged for revert" list for every commit tied to a non-approved ticket

It does **not** classify release types, compute version numbers, write `release-config.json`, create Jira tickets, or run the pipeline — that logic lives in the `/github-release-pipeline` command (Option A).

#### 2. Create/Update JIRA Release Ticket

Invoke the `jira-release-ticket` skill directly:

```
> Use the jira-release-ticket skill to create a release ticket
```

The jira-release-ticket skill supports two modes:

- **Create** — Creates a new `[DD-MM-YYYY] Mesh Components Release` task in RDKB with priority P1, component `meta-rdk-comcast-broadband`, branch `stable2`
- **Update** — Populates or updates the description table on an existing release ticket (with sanity checks: correct title format, RDKB project, valid status, created within 14 days)

Both modes format the release tracking table in JIRA wiki markup and write it to the ticket description.

### Reviewing the Release Config

**This is a critical manual step.** The generated `release-config.json` is the source of truth that drives the release pipeline. A maintainer must review it before proceeding — whether it was generated by the `/github-release-pipeline` command or assembled manually.

Verify for each repository entry:
- `new-version` — Correct version bump
- `commits-to-revert` — Only intended commits are listed for revert
- `summary` — Autonomous-decision rationale for the repo (when generated by the pipeline command) makes sense
- No unexpected repositories included

Example config structure:
```json
{
  "rdk-gdcs/wifi-mesh-experiments": {
    "current-version": "v1.7.0",
    "new-version": "v1.8.0",
    "commits-to-revert": [],
    "pull-request": "",
    "pr-commit": "",
    "summary": ""
  }
}
```

| Field | Description |
|-------|-------------|
| `current-version` | Latest release tag currently on `main` |
| `new-version` | Target version to release |
| `commits-to-revert` | Full SHA hashes to revert before release (e.g., non-approved changes) |
| `pull-request` | Populated by Stage 1 of the pipeline (PR URL) |
| `pr-commit` | Populated by Stage 2 of the pipeline (merge commit SHA) |
| `summary` | Markdown rationale for the autonomous decisions made for this repo (populated by `/github-release-pipeline`) |

### Running the Release Pipeline Manually

If you did not use `/github-release-pipeline` (Option A above), or want to run a stage yourself, execute `release-pipeline.sh` directly once the config is reviewed and approved.

The `-f/--file` and `-s/--stage` flags are both **mandatory**:

```bash
./release-pipeline.sh -f release-config.json -s 1
```

**Stage 1 - Create Release PRs:**
- Creates `release/<version>` branches from `develop`
- Reverts specified commits (if any)
- Opens PRs targeting `main`
- Updates config with PR URLs
- Skipped for repos where `pull-request` is already set in the config

**Stage 2 (`-s all`) - Merge & Release:**
- Validates PR merge readiness
- Merges PRs into `main`
- Creates GitHub releases with auto-generated notes
- Merges release tags back into `develop`
- Updates config with merge commit SHAs
- Skipped for repos where `pr-commit` is already set in the config

> ⚠️ Stage 2 (`-s all`) merges PRs and triggers releases/tags — it cannot be easily undone. Always run stage 1 first, get PRs reviewed/approved, then run stage 2 yourself. The `/github-release-pipeline` command will never run stage 2 on your behalf.

#### CLI Options

```
Usage:
  release-pipeline.sh -f <config.json> -s <1|all> [OPTIONS]

Required:
  -f, --file <path>       Path to the release config JSON file
  -s, --stage <1|all>     Run only stage 1, or the full pipeline (mandatory)

Options:
  -b, --base <branch>     Base branch to create release from (default: develop)
  -r, --repo <name>       Process only the specified repo (e.g., rdk-gdcs/repo-name)
  -y, --yes               Skip merge/release confirmations (auto-approve)
  -d, --dry-run           Show what would be done without making changes
  -h, --help              Show this help message and exit
  -v, --version           Show script version
```

#### Dry Run

Always recommended before the actual release:
```bash
./release-pipeline.sh -f release-config.json -s all --dry-run
```

#### Single Repository

To process only one repository:
```bash
./release-pipeline.sh -f release-config.json -s all -r rdk-gdcs/wifi-mesh-experiments
```

### Update JIRA Ticket Post-Release

After stage 2 completes, resume the OpenCode session (or the `/github-release-pipeline` chat if you used Option A). The workflow will:

1. Read the updated `release-config.json` (now populated with `pull-request` and `pr-commit` values)
2. Update the release tracking table with `GitHub PR main` and `Component Release Commit Hash` columns
3. Push the completed table to the JIRA release ticket via the `jira-release-ticket` skill

## Idempotency

The pipeline is idempotent. If interrupted:
- Stage 1 skips repos that already have a `pull-request` entry in the config
- Stage 2 skips repos that already have a `pr-commit` entry

You can safely re-run the script and it will pick up where it left off.
